# Numerical testing

Use result-first Scientific Software Test-Driven Development for scientific code.

## Start from a scientific expectation

Before implementation when feasible, define a complete reference case or falsifiable relation:

- inputs, units, basis, domain, and model or method version;
- expected value, trend, invariant, relation, or convergence behavior;
- exact source or derivation;
- comparison metric;
- tolerance and tolerance rationale;
- failure meaning.

Preferred references are literature values and accepted experiments. Analytic solutions, standards, independently implemented methods, limiting behavior, conservation relations, and repository-approved baselines are also valid when their independence and limits are clear.

## Select tests by scientific risk

Use the smallest set that can expose plausible scientific corruption:

- literature or experimental reproduction;
- analytic or manufactured solutions;
- conservation and dimensional invariants;
- symmetry, limiting behavior, monotonicity, and other metamorphic relations;
- grid, step, sample, or solver convergence;
- cross-method or independent-implementation comparison;
- parameter sensitivity and uncertainty propagation;
- previous-failure cases for demonstrated numerical failures;
- conventional interface tests only where parsing, units, indexing, or data transformation could alter results.

A correction may retain one result-level previous-failure check for the exact
failing case, proposed in the same approval as the fix.

Do not create a test for every function, mirror private implementation details, enforce a test pyramid, pursue coverage percentages, or preserve weak tests after the scientific behavior disappears. Coverage may reveal unexercised code; it does not establish scientific correctness.

## Retain, revise, or remove

The test owner records this disposition; it is not a generic Review checklist.
Review every added or materially affected test by the distinct failure it can
expose, independence of its reference value or relation, metric and tolerance
rationale, durability across legitimate implementation changes, duplication
with stronger result-level evidence, and measured runtime.

- **Keep:** protects a distinct scientific or required interface risk with an
  independent reference, justified comparison, and pragmatic runtime.
- **Revise:** protects a real risk but duplicates stronger evidence, uses a
  circular or unexplained comparison, encodes a private shape, or belongs in an
  explicit validation command.
- **Remove:** protects no distinct risk or exists only to exercise code or fix
  one implementation arrangement.

Reject by default: coverage targets; per-helper and private-shape tests; exact
requirements prose, workflow wording, logs, hashes, or broad snapshots;
duplicate smoke tests; expected values generated by the implementation under
test; tolerances copied from solver settings without scientific rationale;
test-only branches and configuration; and generic solver tests containing one
campaign's route, filenames, bounds, fixtures, or example assumptions.

Measure runtime using repository commands. Keep fast interface, invariant,
reference, and sentinel checks in the normal gate. Put justified convergence,
sensitivity, uncertainty, and campaign breadth in explicit validation commands
and report their measured time. Do not impose one universal time limit.

## Evidence ownership and minimality

Assign each failure to the smallest durable check that can expose it:

| Failure meaning | Preferred owner |
|---|---|
| termination, residual, feasibility, or constraints | numerical test |
| refinement, tolerance, initialization, scaling, or seed sensitivity | sentinel case or explicit validation sweep |
| conservation, bounds, normalization, symmetry, stability, or limits | scientific invariant test |
| disagreement with an analytic, independent, published, or experimental reference | reference test |
| changed persisted metric or manuscript number | claim-recomputation test |
| figure regeneration or visual completeness | figure validation command |
| LaTeX, citation, cross-reference, or PDF freshness | manuscript build command |

Before adding a helper, fixture, abstraction, or test, ask whether an existing result-level check or reference case already covers the distinct failure. Keep one check per distinct scientific risk, merge cases with the same oracle and tolerance, and move expensive breadth to an explicit validation command. Simplify by removing duplication, never by weakening a tolerance or deleting validation that protects the claim.

## Tolerances

The agent proposes; the user or repository decides. Separate:

- source rounding and digitization;
- measurement and reference uncertainty;
- floating-point and solver stopping error;
- discretization or sampling error;
- variation between legitimate methods;
- scientific acceptance for the intended use.

Prefer a metric tied to the quantity: absolute error near zero, relative error away from zero, weighted or uncertainty-normalized residuals for heterogeneous data, and norm or conservation measures for fields and balances. Avoid one unexplained epsilon across unrelated quantities.

## Test order

1. Encode the result-level expectation and show that the absent or faulty implementation cannot satisfy it.
2. Implement the smallest clear scientific route.
3. Add narrower tests only when the result-level failure does not locate a realistic corruption risk.
4. Run convergence, sensitivity, uncertainty, and independent comparisons required by the claim.
5. Remove disposable diagnostics and obsolete checks.

For suitable new C, C++, Fortran, or mixed-language numerical repositories, Meson is a reasonable compiled default. Preserve an established build system and do not introduce Meson for a Python-only analysis. Typical commands are `meson setup`, `meson compile -C build`, and `meson test -C build`.

The practical test-driven guidance in Teschner (2020, https://arxiv.org/abs/2010.03896) provides useful scientific examples, but its universal micro-test rules and coverage confidence are not doctrine here. The oracle strategies summarized by Kanewala and Bieman (2014, https://doi.org/10.1016/j.infsof.2014.05.006) support analytic, experimental, pseudo-oracle, and metamorphic approaches when exact expected values are unavailable.
