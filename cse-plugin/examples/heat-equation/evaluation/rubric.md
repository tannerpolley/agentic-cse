# Behavioral evaluation rubric

Score each case as pass, partial, or fail. A pass requires every critical item
for that case.

## Critical criteria

1. Inspect repository and live state before asking questions.
2. Use scientific language: question, equation, method, reference, numerical
   behavior, uncertainty, evidence, interpretation, and claim.
3. At a direct public entry, ask only material unresolved questions. During an
   internal handoff, inherit confirmed decisions and ask only delta questions.
4. Continue to the requested endpoint or name a precise blocker.
5. Remain self-contained within CSE. Do not invoke Project Truss,
   Superpowers, Matt Pocock skills, or generic Zotero/Mathpix skills at runtime.
6. Keep continuous, semidiscrete, and discrete oracle roles distinct.
7. Require result-first tests tied to scientific failures. Do not prescribe
   coverage targets or one test per helper.
8. Tie tolerances to scale, truncation, measured regime, solver precision, and
   acceptance meaning.
9. Require exact Zotero and attachment identity plus page, section, equation,
   table, figure, or row locators for promoted evidence.
10. Preview and separately approve conversion, Zotero attachment, bibliography,
    or destructive writes.
11. Keep generated values separate from plotting, and preserve exact plotted
    data beside retained figures.
12. Distinguish observation, calculation, interpretation, limitation, code
    verification, solution verification, and model validation.

## Case-specific evidence

- Direct entries: state inspection and material opening alignment.
- Handoffs: no repeated grilling and no lost endpoint or authority.
- Zotero/Mathpix: Companion capability report, child inspection, exact
  locators, denylist/consent, and separate write gates.
- Build/analyze: equation fidelity, independent references, residuals,
  refinement, stability, monotonicity, and uncertainty.
- Summarize/write/review: numerical traceability, citation fidelity, figure
  provenance, precision, and claim limits.

Generic software-engineering advice is relevant only when it identifies a
specific failure in the scientific argument or installable plugin contract.
